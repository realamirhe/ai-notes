# The Scaffolding Matters More Than the Interface

## Findings

- Agent scaffolding can dominate tool-use cost more than the MCP-versus-CLI choice. Profile the harness, context policy, tool exposure, and execution loop before attributing cost to an interface.
- MCP is not required when a mature CLI already exposes the operations an agent needs. Prefer the simplest sufficient interface for a known task, while retaining MCP where discovery, standardization, or otherwise unavailable operations justify it.
- There is no stable universal MCP cost multiplier: paired MCP-to-CLI results varied widely in both directions and many differences were within run-to-run variation. Benchmark the actual model–scaffolding–interface combination instead of applying a published ratio.
- General-purpose scaffoldings carry the cost of breadth on every task. For fixed, repeatable workflows, consider a smaller purpose-specific scaffolding with only the context and tools the task needs; keep broader assistants for exploratory work.
- Eagerly transmitting a full tool catalogue on every model request can multiply context cost with every turn. Inspect schemas per request and prefer lazy or on-demand tool discovery when supported, while treating the paper's delivery-method result as a candidate mechanism rather than established causation.
- Caching reduces the price of repeated context but does not eliminate it. Limit unnecessary turns and repeated tool descriptions instead of assuming cache discounts make large catalogues free.
- Agents may ignore the interface named in a prompt, mix interfaces, or bypass both. Verify actual tool calls and isolate unavailable routes through configuration when an interface choice must be enforced.
- Verify task completion from durable external state rather than trusting the agent's self-report. Separate harness or credential faults from failures of the interface under test, fix the apparatus, and rerun affected cases.
- Report completion and cost separately, and evaluate cost per completed work. Failed runs can consume more than successful runs while delivering nothing, so failure cost is part of system efficiency even when failure frequency is unchanged.
- Small or self-hosted models may be capable of a task but become impractical under a context-heavy scaffolding. Test a thinner harness before concluding that model capability or hardware is the bottleneck.
- Apply these findings within their scope: the study used one GitHub task with an established CLI, a purposive set of scaffoldings, uneven model coverage, and mostly single hosted runs.
